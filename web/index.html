Architectural Comparison: Normal Banking vs Bank OS

Demonstrating why naive web CRUD apps fail under high concurrency without OS process management.

Scenario: Account A101 starts with ₹50,000. Two concurrent ATM transactions arrive at the same millisecond: [T1: Withdraw ₹40,000] and [T2: Withdraw ₹30,000].

1. Standard Banking CRUD App

RACE CONDITION

Direct SQL execution without synchronization:

  • T1 reads balance: ₹50,000 (Checks 50k >= 40k -> OK)
  • T2 reads balance simultaneously: ₹50,000 (Checks 50k >= 30k -> OK)
  • T1 debits ₹40,000 -> writes ₹10,000
  • T2 debits ₹30,000 -> writes ₹20,000 (or -₹20,000)
❌ Result: ₹70,000 dispensed from a ₹50,000 account! Critical bank overdraft and lost updates.

2. Bank OS Simulator

MUTUAL EXCLUSION

OS Process Management + Round Robin + Mutex Locking:

  • T1 scheduled on CPU -> Acquires Mutex Lock on A101
  • T2 scheduled -> Attempts to access A101 -> Blocked to WAITING queue (yields CPU!)
  • T1 debits ₹40,000 -> Updates balance to ₹10,000 -> Commits -> Releases Lock
  • T2 unblocks to READY queue -> Reads updated balance ₹10,000 -> Checks 10k < 30k -> ROLLBACK (Rejected)
✓ Result: Data consistency preserved. Final balance is safely ₹10,000. T2 correctly rejected for insufficient funds.
