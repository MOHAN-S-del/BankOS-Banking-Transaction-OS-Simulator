DBMS & OPERATING SYSTEM CONCEPTS IMPLEMENTED IN BANKOS

Core computer science theory applied to high-throughput financial switch architecture.

OS CONCEPT 01

Process Control Block (PCB)

Every banking transaction is instantiated as an independent OS process managed by a ProcessControlBlock struct. Tracks PID, state machine, discrete arrival tick, remaining burst cycles, and lock dependencies.

Simple Explanation: Instead of treating a bank payment as a simple database query, BankOS treats it like a program running in an OS, with its own process ID, memory registers, and execution states.
NEW ➔ READY ➔ RUNNING ➔ WAITING ➔ TERMINATED
PCB = { PID, Type, State, Burst, Arrival, Locks, WaitTicks }
OS CONCEPT 02

MLFQ Scheduling & Anti-Starvation Aging

Dual-queue architecture prevents Head-of-Line blocking. Queue 1 (SRTF) fast-tracks UPI & ATM transactions. Queue 2 (Round Robin, Q=5) time-slices heavy payrolls. To prevent starvation, processes waiting > 50 ticks are dynamically elevated to Q1.

Simple Explanation: Fast UPI payments never get stuck behind massive salary runs. If a salary run waits too long, an automatic elevator promotes it so it is guaranteed to finish.
Priority: Queue 1 (SRTF) > Queue 2 (Round Robin, Q=5)
Aging Rule: If WaitTime(P) ≥ 50 ticks ➔ Promote(P, Queue 1)
DBMS CONCEPT 03

Two-Phase Locking (2PL) & Deadlock Denial

Guarantees serializability through strict Two-Phase Locking: Phase 1 (Growing Phase) acquires account locks; Phase 2 (Shrinking Phase) releases all locks at transaction termination. Deadlocks are denied via Havender monotonic lock ordering.

Simple Explanation: To prevent two people from spending the same balance at the exact same millisecond, accounts are locked. By locking lower Account IDs first, deadlocks are mathematically impossible.
Havender Rule: Lock First = min(AccA, AccB) < Lock Second = max(AccA, AccB)
Coffman #4 Denial: Circular wait is mathematically impossible (0% Deadlocks)
DBMS CONCEPT 04

ACID Guarantees & Atomicity Rollback

BankOS enforces ACID guarantees. Atomicity is validated through real-time rollbacks: if an account has insufficient funds (e.g. Account #1005 with ₹300), the transaction aborts and executes a full ROLLBACK—zero partial debits.

Simple Explanation: A transfer either succeeds 100% or fails 100%. If money cannot be credited to the receiver, money is never deducted from the sender.
Atomicity: If (Balance < Amount) ➔ ROLLBACK; State = TERMINATED_FAILED
Consistency: Debit(From) == Credit(To) • Balance ≥ 0.00
