MOTIVATION & CORE CHALLENGES

The Three Bottlenecks in Modern Banking Systems

1. Flash Contention Spikes

Scenario: Festive shopping surges, flash sales, and UPI peak windows push thousands of transfers into the same hotspot accounts.

The Failure: Optimistic Concurrency Control (OCC) triggers massive abort storms (>35% failed retries), saturating database CPU.

2. Transaction Starvation

Scenario: Continuous high-frequency consumer UPI micro-payments flood the queue ahead of large corporate payroll batches.

The Failure: Without anti-starvation mechanisms, large salary transfers wait indefinitely, missing clearing cutoffs.

3. Circular Deadlocks

Scenario: Reciprocal transactions: User A sends ₹1,000 to User B while User B simultaneously sends ₹500 to User A.

The Failure: Mutually waiting threads lock both accounts, causing Coffman's circular wait and freezing threads.

OPERATING SYSTEMS CORE

Multi-Level Feedback Queue (MLFQ) & Anti-Starvation

Queue 1: Shortest Remaining Time First (SRTF)

• Workload: Retail UPI consumer micro-payments (CPU burst = 1-2 ticks).

• Behavior: Preemptive priority. Shorter transactions clear immediately with sub-millisecond response latency, eliminating transaction bottlenecks.

Queue 2: Round Robin (Quantum Q = 5 Ticks)

• Workload: Heavy corporate salary batches and ATM hardware cycles.

• Preemption: Preempts jobs after 5 ticks to prevent monopolization of CPU cores.

Anti-Starvation Aging Elevator (Threshold X = 30 Ticks)

• The Problem: When continuous high-volume UPI traffic floods Queue 1, Queue 2 jobs would starve indefinitely.

• The Mechanism: The kernel monitors waiting time in Queue 2. When a process exceeds 30 ticks, it is automatically promoted into Queue 1 ahead of incoming traffic!

if (current_tick - pcb.arrival_tick >= AGING_THRESHOLD) { promote_to_queue1(pcb); // Guarantees bounded wait time! total_aging_promotions++; }
DATABASE CONCURRENCY CONTROL

Strict Two-Phase Locking (2PL) Serializability

Phase 1: Growing Phase

• Lock Acquisition: Before a transaction enters the CPU RUNNING state, it requests exclusive write locks on Sender & Receiver accounts.

• Contention Chamber: If locks are held, the process transitions to WAITING. Zero partial state mutations allowed.

Phase 2: Lock Point (ALU)

• Peak Concurrency State: All required account locks are fully held.

• Isolated Balance Mutation: The CPU core executes the balance verification and arithmetic debit/credit in 100% isolation.

Phase 3: Shrinking Phase

• Strict 2PL Invariant: Locks are never released prematurely during execution.

• Atomic Release: All locks are simultaneously released only when the transaction finishes COMMIT or ROLLBACK. Eliminates cascading aborts.

DEADLOCK PREVENTION THEORY

Deadlock Elimination: Havender Monotonic Ordering

The Mutual Deadlock Risk (Coffman Circular Wait)

Transaction 1: Transfer from Account #1001 to Account #2001.

Transaction 2: Transfer from Account #2001 to Account #1001.

Naive Execution: Tx 1 locks #1001 & waits for #2001. Tx 2 locks #2001 & waits for #1001. Both threads freeze indefinitely.

The Havender Solution: Strict Ascending Lock Hierarchy

// Havender Ascending Ordering: int first_lock = min(from_account, to_account); int second_lock = max(from_account, to_account); acquire_lock(first_lock); acquire_lock(second_lock);

• Coffman #4 Denial: Circular wait is mathematically impossible.

• Result: Zero deadlocks without expensive cycle detection graphs!

RELATIONAL ALGEBRA FOR FACULTY REVIEW

Multi-Table SQL JOIN: Resolving Senders & Receivers

SELECT t.TxID, t.Amount, t.Status AS TransactionStatus, sender_cust.FullName AS SenderCustomer, t.FromAccount AS SenderAccount, receiver_cust.FullName AS ReceiverCustomer, t.ToAccount AS ReceiverAccount, branch.BranchName AS SenderBranch, t.CreatedAt AS ExecutionTime FROM Transactions t INNER JOIN Accounts sender_acc ON t.FromAccount = sender_acc.AccountID INNER JOIN Customers sender_cust ON sender_acc.CustomerID = sender_cust.CustomerID LEFT JOIN BankBranches branch ON sender_acc.BranchID = branch.BranchID INNER JOIN Accounts receiver_acc ON t.ToAccount = receiver_acc.AccountID INNER JOIN Customers receiver_cust ON receiver_acc.CustomerID = receiver_cust.CustomerID ORDER BY t.TxID DESC LIMIT 25;

✓ 3NF Normalized: Eliminates data redundancy while providing full audit resolution in <1.0ms.
